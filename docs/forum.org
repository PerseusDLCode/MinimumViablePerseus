** Researching milestones in Perseus Corpora

** Improving Chunking Strategies
:PROPERTIES:
:CUSTOM_ID: improving-chunking-strategies
:END:
The current implementation works for our first iteration, but it now needs to be generalized.

1. Xslt_stylesheet values are hard-coded in xslt_stylesheet properties: one for chunking by div, one for chunking by milestone.  Will chunking strategy ever vary depending on other TEI document properties?

2. We've already mentioned P4's multiple-chunking feature: users could choose to chunk by, say, book, or by chapters within a book. How urgent a feature is that to implement?

3. The set of possible strategies is hard-coded in StrategySelector's class variable _STRATEGIES.  This seems brittle. Is there a way to use some sort of registry, and then be able to pass in a list of units -- say, from a config file?

4. I'm not sure about the claim in the docString for StrategySelector that milestone-based chunking is the (more) common case. This is going to require some research. Are all milestones candidates for chunking? What makes milestones a higher priority than div types/subtypes?

5. I want to examine the claim that "encoding inconsistencies in the Perseus corpus mean that refsDecls cannot always be trusted." I know the encoding is inconsistent, but why does that make the refsDecls unreliable? Is there a reason why editors cannot revise the refsDecls to make them reliable? It seems to me the responsibility for accurate structuring (prerequisite for chunking) lies with the editor, not the compiler. The consequences for us would be significant: we wouldn't have to calculate a chunking strategy; we would simply use the refsDecls.

** Making XSLT Customizable
:PROPERTIES:
:CUSTOM_ID: making-xslt-customizable
:END:
We've already designed our chunking stylesheets to be imported by more specialized stylesheets, but our chunking-strategy selection algorithm doesn't allow us to take advantage of that. There should, I think, be metadata somewhere (in a big table; in a sidecar xml file next to the TEI file) that allows editors to specify which XSLT stylesheet (or stylesheet family) should be used to process the text into HTML. Or plural stylesheets: each refsDecl gets a stylesheet assignment?

In other words, I propose that responsibility for choosing how a TEI document is rendered into HTML should lie with the editors and not be something that's calculated. As I recall that's actually how P4 (at least the Perl-based P4) worked.

** Walking back poor encoding decisions
This section is opinionated, but I want to make some cases for the stakeholders (especially Greg) to consider.

*** The use of the Epidoc schema for documents that aren't epigraphic or papyrological
I've been told that at some point, the developers decided to enforce the use of Epidoc simply because it was the sparest TEI schema they could find.  These developers seem to have been unaware that the TEI schema is /meant/ to be customized, and that they could have created their own TEI customization more closely tailored to the Perseus corpus.

*** Failure to use xml:base to specify CTS urns.
In the current editions, the base CTS urn is specified in an @n attribute on the top-most div in the <body>:

#+begin_src xml
  <div xml:lang="lat" type="edition" n="urn:cts:latinLit:phi2331.phi013.perseus-lat2">
#+end_src

Perseus tends to use the @n attribute for anything and everything, but in this case that urn should be specified with the @xml:base attribute:
#+begin_src xml
  <div xml:lang="lat" type="edition" xml:base="urn:cts:latinLit:phi2331.phi013.perseus-lat2">
#+end_src

That type="edition" encoding is also a poor choice: that kind of metadata belongs somewhere in the TEIHeader.

The fact is -- here's the polemical part -- there was a generation of Perseus developers who had scant knowledge of the TEI and an active dislike of XML. As a result, they damaged the Perseus corpus by trying to shoe-horn it into Epidoc and making poor use of TEI features (like xml:base). I don't know how extensive the damage is, nor do I know how difficult it would be to repair it. But in some cases, at least -- fixing refsDecls, moving to Perseus-specific TEI customizations instead of Epidoc -- I think we would improve the work we're doing on Perseus 6 if we took some restorative actions.

** Linguistic Annotation of TEI documents
Charles has developed a method in kodon <https://github.com/PerseusDLCode/kodon-py> for adding morphological tagging to Perseus's TEI documents, but it involves using his own, idiosyncratic TEI XML parser to generate a JSON representation, operating on the JSON, and then somehow converting it back to XML.  I think developing a bespoke XML parser is a bad design choice; however, I do understand that available lemmatizers work on plain text, not XML.

The TEI schema includes elements and attributes that support linguistic annotation of corpora (see https://tei-c.org/release/doc/tei-p5-doc/en/html/CC.html#CCAN and https://tei-c.org/release/doc/tei-p5-doc/en/html/AI.html#AILA). It may be that the TEI's elements are insufficient for Perseus's use, but I fear Charles and other developers have abandoned TEI XML prematurely because they dislike XML and prefer to work with JSON. I have the advantage and disadvantage of not being a classical philologist, and my training in computational linguistics is dated. I'd like to spend some time answering the naive-sounding question: "Why can't we just do this in TEI XML?"

[[https://tei-c.org/release/doc/tei-p5-doc/en/html/AI.html#AILALW][Section 18.4.2]] in the Guidelines discusses the needs of corpus linguists and how the TEI may be used to address them. We need to study this carefully.

*** Research Task
Find research papers that discuss practical uses of TEI linguistic markup. What projects have used it? What barriers or limitations did they encounter? If they chose not to use TEI markup to perform linguistic annotation, what did they use instead, and why?

Here's a prototype that generates a <tokens> document containing one
<token> element per orthographic word, containing the surface form and
an anchor pointing to its containing element:

#+begin_src xml
  <?xml version="1.0" encoding="UTF-8"?>
  <xsl:stylesheet
      xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
      xmlns:tei="http://www.tei-c.org/ns/1.0"
      xmlns:xs="http://www.w3.org/2001/XMLSchema"
      version="3.0"
      exclude-result-prefixes="tei xs">

    <!--
      TEI Token Extractor — Stage 1 of the Perseus6 annotation pipeline.

      Input:  A TEI-encoded text document (any structural convention).
      Output: A <tokens> document: one <token> per orthographic word,
              carrying the surface form and an anchor pointing to its
              containing element.

      Design decisions:
      - No assumptions about div/@type or milestone structure.
      - Apparatus elements are excluded: <note>, <del>, <rdg>,
        <supplied>, <gap>, <unclear> (configurable via $exclude-elements).
      - Punctuation is stripped from leading and trailing positions of
        each whitespace-delimited token.  The raw form is preserved in
        @raw for diagnostics.
      - xml:id is used for element anchors when present; generate-id()
        is used as a fallback for elements without @xml:id.  Stable
        anchors require explicit @xml:id on citable elements in the source.

      XPath 3.0 regex character class rules (relevant to this file):
      Inside a character class [...]:
        \]   escape the closing bracket
        \\   escape a literal backslash
        -    place at start or end of class to mean literal hyphen
        ^    special only as the very first character (negation)
        All other characters are literal, including Unicode.
        Writing \X where X is not a regex metacharacter is an ERROR.

      The punctuation class used here is written as a plain string
      attribute value.  XML escaping (&lt; for <, &gt; for >, &quot;
      for ") is resolved by the XML parser before the XPath engine sees
      the string, so the regex receives the intended literal characters.
      The apostrophe/single-quote is excluded from the class because
      it would conflict with the XPath attribute delimiter; it is handled
      by a separate replace() call using a double-quoted string.
    -->

    <xsl:output method="xml" indent="yes" encoding="UTF-8"/>

    <!-- Elements whose text content should be suppressed entirely.
         Add or remove names as corpus analysis dictates.             -->
    <xsl:param name="exclude-elements" as="xs:string*"
               select="('note', 'del', 'rdg', 'supplied', 'gap', 'unclear',
                        'figDesc', 'label')"/>

    <!--
      strip-punct: remove leading and trailing punctuation from a token.

      The function applies four replace() calls in sequence:
        1. Strip leading chars from the main punctuation class
        2. Strip trailing chars from the main punctuation class
        3. Strip leading apostrophes/single-quotes (separate string)
        4. Strip trailing apostrophes/single-quotes (separate string)

      Main punctuation class characters:
        .,;:!?    — common ASCII punctuation
        ·         — middle dot / Greek interpunct (U+00B7)
        —–        — em-dash (U+2014), en-dash (U+2013)
        (){}      — parentheses and braces
        \[\]      — square brackets (\] escapes the closing bracket)
        &lt;&gt;  — less-than / greater-than (XML-escaped in source)
        ⟨⟩        — mathematical angle brackets (U+27E8/27E9),
                    used in papyrological / epigraphic EpiDoc texts
        &quot;    — double quotation mark (XML-escaped in source)

      Apostrophe (U+0027) is handled in steps 3–4 using a separate
      double-quoted attribute value, avoiding the XML quoting conflict.
      Note: in Greek, the apostrophe indicates elision and typically
      appears at the END of a token (e.g. δ'), so trailing stripping is
      the important case.
    -->
    <xsl:function name="tei:strip-punct" as="xs:string">
      <xsl:param name="s" as="xs:string"/>
      <!-- Steps 1–2: main punctuation class (single-quoted attribute) -->
      <xsl:variable name="s1"
        select="replace($s,
                  '^[.,;:!?·—–(){}\[\]&lt;&gt;⟨⟩&quot;]+', '')"/>
      <xsl:variable name="s2"
        select="replace($s1,
                  '[.,;:!?·—–(){}\[\]&lt;&gt;⟨⟩&quot;]+$', '')"/>
      <!-- Steps 3–4: apostrophe / single-quote (double-quoted attribute) -->
      <xsl:variable name="s3" select="replace($s2, &quot;^'+&quot;, '')"/>
      <xsl:variable name="s4" select="replace($s3, &quot;'+$&quot;,  '')"/>
      <xsl:sequence select="$s4"/>
    </xsl:function>

    <!-- ============================================================ -->
    <!-- Root: emit a <tokens> wrapper with document metadata.        -->
    <!-- ============================================================ -->

    <xsl:template match="/">
      <xsl:variable name="urn"
                    select="(//@n[starts-with(., 'urn:cts')])[1]"/>
      <xsl:variable name="lang"
                    select="(//@xml:lang)[1]"/>
      <tokens>
        <xsl:if test="$urn">
          <xsl:attribute name="urn" select="$urn"/>
        </xsl:if>
        <xsl:if test="$lang">
          <xsl:attribute name="xml:lang" select="$lang"/>
        </xsl:if>
        <xsl:apply-templates select="//tei:body"/>
      </tokens>
    </xsl:template>

    <!-- ============================================================ -->
    <!-- Suppress excluded elements and their descendants entirely.   -->
    <!-- ============================================================ -->

    <xsl:template match="tei:*[local-name() = $exclude-elements]"
                  priority="10"/>

    <!-- ============================================================ -->
    <!-- For every other element, recurse into children.              -->
    <!-- ============================================================ -->

    <xsl:template match="tei:*">
      <xsl:apply-templates/>
    </xsl:template>

    <!-- ============================================================ -->
    <!-- Text nodes: tokenize and emit <token> elements.              -->
    <!-- ============================================================ -->

    <xsl:template match="text()">
      <xsl:variable name="anchor"      select="parent::tei:*"/>
      <xsl:variable name="anchor-id"
                    select="if ($anchor/@xml:id)
                            then string($anchor/@xml:id)
                            else generate-id($anchor)"/>
      <xsl:variable name="anchor-name" select="local-name($anchor)"/>

      <!-- Split on whitespace; discard empty strings. -->
      <xsl:variable name="raw-tokens" as="xs:string*"
                    select="tokenize(normalize-space(.), '\s+')
                            [normalize-space(.) != '']"/>

      <xsl:for-each select="$raw-tokens">
        <xsl:variable name="raw"     select="."/>
        <xsl:variable name="surface" select="tei:strip-punct($raw)"/>
        <xsl:if test="normalize-space($surface) != ''">
          <token>
            <xsl:attribute name="surface"  select="$surface"/>
            <xsl:attribute name="raw"      select="$raw"/>
            <xsl:attribute name="anchor"   select="$anchor-id"/>
            <xsl:attribute name="in"       select="$anchor-name"/>
            <xsl:attribute name="position" select="position()"/>
          </token>
        </xsl:if>
      </xsl:for-each>
    </xsl:template>

  </xsl:stylesheet>
#+end_src

***** Implementation
[2026-04-20] Implemented as =src/xslt/add_xml_ids.xsl=.

The stylesheet is a standard identity transform with additional high-priority
templates that intercept citable elements and inject =@xml:id= before passing
through all other attributes and content unchanged.

*Algorithm:*

1. Collect citable unit names from =//tei:refsDecl[@n='CTS']/tei:cRefPattern/@n=,
   normalized to lowercase (some corpora declare ~"Chapter"/"Book"~ with capital
   initials while the corresponding =@subtype= values in the body are lowercase).

2. Match three element types that lack =@xml:id=:
   - =tei:l[@n]= — verse lines, when ~"line"~ is a declared CTS unit
   - =tei:div[@n][not(starts-with(@n,'urn:'))]= — all structural divs with =@n=
     except the top-level edition div (whose =@n= holds the CTS URN). This is
     intentionally broader than the CTS unit list: introductions, prologues, and
     other non-CTS-cited sections must also provide stable anchors.
   - =tei:milestone[@n][lower-case(@unit) = $units]= — milestones that are
     genuine CTS citation units (not page-break or pagination milestones).

3. ID generation function =local:make-id(el)=:
   #+begin_example
   prefix    = lower-case(@subtype) | lower-case(@unit) | local-name(.)
   ancestors = ancestor::tei:div[not(starts-with(@n,'urn:'))]/@n  (doc order)
   id        = string-join((prefix, ancestors, @n), '-')
               → sanitize: replace [^A-Za-z0-9_-] with '_'
   #+end_example
   Example: =tei:l[@n="5"]= inside =div[@subtype="poem"][@n="1"]= → =xml:id="l-1-5"=.

The TEI documents are already using the xml:base attribute to carry a CTS
urn for elemeents in the document tree (and perhaps on
milestones). The xml:base could serve as the basis for the xml:ids (or
maybe replace them altogether).

One problem is the inconsistent use of xml:base in the TEI documents.
Frequently, the xml:base is simply copied from the ancestor element.
E.g.,

#+begin_src xml
  <body>
  	<div type="edition" n="urn:cts:greekLit:tlg0001.tlg001.perseus-grc2" xml:lang="grc">
  		<div type="textpart" subtype="book" xml:base="urn:cts:greekLit:tlg0001.tlg001.perseus-grc2" n="1">
  			<milestone unit="card" n="1"/>
  			<l xml:base="urn:cts:greekLit:tlg0001.tlg001.perseus-grc2:1" n="1">ἀρχόμενος σέο, Φοῖβε, παλαιγενέων κλέα φωτῶν</l>
#+end_src

There are several problems with this example.

***** PROBLEM: Reliance on a <div type='edition'> element to hold critical metadata
*The reliance on a <div type="edition">* CTS URNs have the following
structure, as defined in the specification
(https://cite-architecture.github.io/ctsurn_spec/):

   #+begin_example
   urn:cts:CTSNAMESPACE:WORK:PASSAGE
   #+end_example

The CTSNAMESPACE in our example is greekLit;; the work is a compound
string of its own, corresponding with conventions in classical
studies:

   - *tlg0001* designates a group of works attributed to Apollonius Rhodius;

   - *tlg001* designates a work called "The Argonautica";

   - *perseus-grc2* designates a particular edition of the
     Argonautica: it has been created by Perseus; it is in Greek; and
     it is the second such edition.

This implementation of the WORK portion of the CTS urn is loosely
based on FRBR, and it is flawed in many ways; however, it is well
entrenched and cannot be altered at this point.

Nevertheless, it doesn't belong as an attribute of a <div> element. At
the very least it should be moved up to the <text> or <body> element,
which are required, but ideally it would live in the TEIHeader with
the rest of the metadata.


***** PROBLEM: underspecified text citation hierarchy for the PASSAGE section
The CTS URN specification says the following:

#+begin_quote
The passage component is a hierarchy of one or more levels expressing
a logical citation scheme applying to all versions of a text. A poem
might be cited by the single unit of "poetic line." A prose work might
be cited by a hierarchy such as "book/chapter/section/subsection."
Passage references at any level of the text's citation hierarchy may
identify either a single citable node or a range indicated by the
first and last nodes of the range.
#+end_quote

The notions of a "logical citation scheme" and a text's "citation
hierarchy" are deliberately underspecified; they are idiosyncratic to
a genre (Western drama's traditional act/scene/line), a particular
text (Biblical citations of Book Chapter:Verse), or a scholarly tradition.

Perseus's texts elide explicit definition of citation schemes and
citation hierarchies; they are implicit in the <refsDecl>
elements. Since much of the current state of the Perseus texts has
come as a result of a misplaced adherence to the EpiDoc TEI
customization, many of these refsDecls may well assume the citation
tradition used in epigraphy.

(It is also the case that design of <refsDecl>s was often an
afterthought in the old days.)

Much of the complexity surrounding citation and annotation in Perseus
comes, I think, from a failure to make citation patterns more
explicit. Instead, it is implicit in the one or more <cRefPattern>
elements, which are often lax or overly reliant on implicit text
structure.  For example

#+begin_src xml
  <refsDecl n="CTS">
    <cRefPattern n="line"
                 matchPattern="(\w+).(\w+)"
                 replacementPattern="#xpath(/tei:TEI/tei:text/tei:body/tei:div/tei:div[@n='$1']/tei:l[@n='$2'])">
      <p>This pointer pattern extracts book and line</p>
    </cRefPattern>
    <cRefPattern n="book"
                 matchPattern="(\w+)"
                 replacementPattern="#xpath(/tei:TEI/tei:text/tei:body/tei:div/tei:div[@n='$1'])">
      <p>This pointer pattern extracts book</p>
    </cRefPattern>
  </refsDecl>
#+end_src

1. The match patterns are needlessly greedy.

2. The replacement patterns are based solely on a strict hierarchy of
   <div> elements and make no use of the @type attributes that have
   been added to <div>s, largely for purposes of citation.

3. <cRefPattern>s are meant to be used for citation *resolution*, not
*composition*.

See
https://tei-c.org/release/doc/tei-p5-doc/en/html/SA.html#SACRCS. The
<citeStructure> element seems to have been designed for this purpose,

#+begin_quote
 One advantage citeStructure has is that it can be used to generate canonical references, using the declared citation structure to query the text structure. This means it is possible to automatically produce a list of resolvable citations for a TEI document. 2. <citeStructure> is more difficult to design and process than

***** Implementation
[2026-04-20] Implemented as =src/xslt/tokenize.xsl=.

The tokenizer is a lightly adapted version of the prototype. Key differences
from the prototype:

1. *Anchor resolution* — the =text()= template walks =ancestor::tei:*[@xml:id]=
   (reverse document order, innermost first) rather than using =parent::tei:*=
   directly. This is necessary because text typically lives inside =tei:p=,
   =tei:l=, or other intermediate elements, whose nearest citable ancestor may
   be a =div= or =milestone= several levels up. The =generate-id()= fallback
   from the prototype is removed; an =xsl:message= warning fires instead if no
   citable ancestor is found.

2. *Extended exclude list* — =tei:speaker= and =tei:stage= are added to the
   default =$exclude-elements= parameter. Speaker labels in dramatic texts are
   structural metadata, not linguistic content; stage directions are similarly
   outside the citable text stream.

3. *=strip-punct= function* — identical to the prototype; renamed from
   =tei:strip-punct= to =local:strip-punct= to match the project's namespace
   conventions.

Output format (unchanged from prototype):
#+begin_src xml
<tokens urn="urn:cts:…" xml:lang="grc">
  <token surface="ἄνδρα" raw="ἄνδρα," anchor="l-1" in="l" position="1"/>
  …
</tokens>
#+end_src

** TEI->HTML Stylesheet Family
:PROPERTIES:
:CUSTOM_ID: tei-html-stylesheet-family
:SOURCE: chat/2026-05-21
:END:

The current XSLT pipeline conflates two distinct concerns: chunking
(dividing a TEI document into separately-navigable HTML pages) and
rendering (transforming TEI elements into HTML elements).  This item
records the design of a new stylesheet architecture that separates these
concerns and supports a family of TEI customization-specific rendering
libraries.

*** Research
[2026-05-21]

**** The problem with the current architecture

=chunker_core.xsl= handles both chunking and rendering.  Every rendering
template carries =local:after-start= / =local:before-stop= boundary
guards and declares tunnel parameters (=$start=, =$stop=, =$base-urn=)
whether it uses them or not.  This coupling makes it impossible to reuse
the rendering templates across different chunking strategies or different
page layouts, and it makes adding TEI-customization-specific rendering a
messy proposition.

**** The separation principle

Rendering templates should be completely ignorant of chunking.  A
template for =tei:l= should know how to turn a verse line into HTML; it
should not know whether it is inside a card-milestone chunk or a
div-based chunk, or whether it is near a chunk boundary.

The chunking infrastructure calls into the rendering library by invoking
templates in a named mode (=tei-to-html=) and injecting whatever
context it needs via tunnel parameters.  Rendering templates declare
only the tunnel parameters they actually consume; templates that need
nothing from the chunking layer declare nothing.

**** The xml:base simplification

The =$base-urn= tunnel parameter currently threaded through nearly every
template in =chunker_core.xsl= is only consumed by the =tei:l= template
(to construct =data-cts-urn= and =@id=).  Now that the TEI citation
pipeline normalizes =@xml:base= on all citable elements, the =tei:l=
template can read =@xml:base= directly from the element, eliminating
=$base-urn= as a tunnel parameter entirely.  The precondition is that
=@xml:base= must be present on =<body>= (required for =<citeStructure>=
support); an error should be raised if it is absent.

**** The ODD/stylesheet correspondence

The Perseus schema family is a hierarchy of TEI ODD customizations:

- =Perseus_base= :: elements common to all Perseus texts (prose,
  verse, drama, lexica, …).  Chains from =tei_bare=.
- =Perseus_drama= :: adds drama module elements (=sp=, =speaker=,
  =stage=, etc.)
- =Perseus_greek_tragedy= :: adds genre-specific div types
  (=prologue=, =parados=, =stasimon=, =exodos=, …)
- =Perseus_dict= :: adds TEI dictionary module elements
- Further specializations as needed

Each ODD has a corresponding XSL rendering library.  The element list
in the ODD's =<schemaSpec>= is the manifest for the stylesheet: every
included element needs a template.

**** The stylesheet architecture

*Rendering libraries* (one per ODD level):
- =perseus_base.xsl= — templates for all elements in =Perseus_base=,
  operating in =mode="tei-to-html"=.  No root template; no page shell.
  Pure library.
- =perseus_drama.xsl= — imports =perseus_base.xsl=; adds/overrides
  templates for drama elements.
- =perseus_greek_tragedy.xsl= — imports =perseus_drama.xsl=; adds
  templates for tragedy-specific div types.
- etc.

*Chunking infrastructure* (unchanged in responsibility, revised in
interface):
- =chunker_core.xsl= — boundary logic (=local:before-stop=,
  =local:after-start=), helper functions.  Calls rendering templates
  via =<xsl:apply-templates mode="tei-to-html">=.

*Driver files* (one per layout/parameter variant):
- Import the appropriate rendering library for the text's schema.
- Import the chunking infrastructure.
- Define the root template, page shell, and global parameters.
- Different drivers can produce different layouts (three-column reader,
  print-oriented single page, etc.) while reusing the same rendering
  chain.

Example import graph for a milestone-chunked Greek tragedy reader:

#+begin_example
greek_tragedy_reader.xsl          ← driver: page layout, parameters
  ├── perseus_greek_tragedy.xsl   ← rendering: tragedy div types
  │     └── perseus_drama.xsl    ← rendering: sp, speaker, stage
  │           └── perseus_base.xsl  ← rendering: p, l, div, hi, note…
  └── chunker_core.xsl            ← chunking: before-stop, after-start
#+end_example

A print driver for the same text reuses the rendering chain entirely:

#+begin_example
greek_tragedy_print.xsl
  ├── perseus_greek_tragedy.xsl   ← same chain
  └── single_page_core.xsl       ← different pagination strategy
#+end_example

**** Open questions

1. The =mode="tei-to-html"= name is a proposal.  Any objection to it?

2. =chunker_core.xsl= currently uses =mode="chunk"=.  Should that be
   renamed to =tei-to-html= (unifying the mode), or kept separate so
   that the chunking infrastructure can distinguish its own structural
   templates from the rendering templates it delegates to?

3. What is the right scope for =Perseus_base=?  The current ODD draft
   was built up to handle the /Poetics/ and may include unnecessary
   elements or be missing others.  A corpus-wide survey of element
   usage (analogous to the milestone survey) would give a principled
   answer.  =tei:seg= and =tei:ab= are two candidates that may be needed
   in the base.

4. =att.metrical= is currently included in =Perseus_base=.  Should it
   move to a =Perseus_verse= child schema, given that prose texts like
   Thucydides have no use for it?

   - Answer :: The Thucydides text does, in fact, encode a metrical
     line: a quote from an oracle. This illustrates a general point:
     the boundary between "base" and "verse" isn't purely genre-based.
     The right heuristic isn't "does this text belong to a verse
     genre?" but "can this element appear with this attribute in any
     Perseus text regardless of genre?" By that test, =att.metrical= on
     =tei:l= passes, because oracle quotations, epigraphs, and the like
     show up everywhere.

*** Research (continued)
[2026-05-21]

**** The mode boundary in detail

The two-mode architecture settles into a precise contract:

- =mode="chunk"= :: owned by =chunker_core.xsl=.  Traverses the
  document tree, applies =local:before-stop= / =local:after-start=
  boundary guards at each level, and suppresses nodes outside the
  current chunk's range.  When a node passes the boundary test, it
  delegates to =mode="tei-to-html"= for rendering.  Never produces
  HTML element content directly; that is always the rendering library's
  responsibility.

- =mode="tei-to-html"= :: owned by =perseus_base.xsl= and its
  descendants.  Transforms TEI elements into HTML elements.  Has no
  knowledge of chunk boundaries, no =$start= / =$stop= parameters, and
  no =local:before-stop= guards.  Receives a node and produces HTML,
  full stop.

The handoff is a single =<xsl:apply-templates mode="tei-to-html"/>= in
each chunk-mode template that passes the boundary test.

**** Why the straddling case requires Option B

Pre-filtering a flat node sequence before rendering (Option A) cannot
handle the case where a chunk boundary falls inside a structural
element — a =tei:div= that straddles a milestone boundary, for
instance.  The boundary check must happen recursively during tree
traversal, which is why it lives in =mode="chunk"= templates rather
than in a pre-pass.

**** Tunnel parameters across the boundary

The rendering library needs no tunnel parameters from the chunking
layer.  Specifically:

- =@xml:base= :: not needed as a tunnel parameter.  In the
  =<citeStructure>= architecture, =@xml:base= is on =<body>=;
  any rendering template that needs the base URN can reach it via
  =ancestor::tei:body/@xml:base=.  An error should be raised at
  compile time if =<body>= lacks =@xml:base=.

- =$morph-url= and citation links :: not injected as tunnel
  parameters.  External data needed by the rendering templates
  (morphological analyses, citation link tables) will be compiled
  during the build into XML or JSON sidecar files and loaded at
  render time via the =document()= function.  This keeps the
  static-site contract intact: no runtime server dependency baked
  into the generated pages.

- Pagination and breadcrumbs :: these are properties of the /page/,
  not of any individual TEI element.  The driver's page-shell template
  constructs them from chunk metadata (already pre-collected in
  =$all-chunks= in the current =generate_chunks.xsl=) before
  =mode="tei-to-html"= is ever invoked.  They do not cross the
  mode boundary.

**** Conclusion

No tunnel parameters need cross from =mode="chunk"= into
=mode="tei-to-html"=.  The two modes are genuinely independent.
This contract should be stated explicitly in a comment block at the
top of both =chunker_core.xsl= and =perseus_base.xsl=.

:PROPERTIES:

*** Discussion
**** [2026-05-13 Wed]
We have been studying CiteStructures (See [[id:4EA3889F-245B-4E85-862E-6BA7EE91F364][Citation Structure
Implementation]]).  CiteStructures were introduced into the TEI after
most of Perseus's texts had been encoded, but they seem perfectly
designed to handle our needs now:

- They provide a more concise mechanism for describing canonical
  references than CRefPattern or RefState.
- They can be used to /generate/ canonical references, thus allowing us
  to explicitly define an /annotation surface/ for a document.

  [[https://dtsapi.org/specifications/][Distributed Text Services]] has an implementation that uses
  citeStructures. [[https://github.com/distributed-text-services/MyDapytains][MyDapytains]] is a reference implementation, and we
  should look at what they've done.

**** Questions
How difficult would it be to convert Perseus's corpora from
CRefPatterns and RefStates to CiteStructures?

Let's take Aristotle's /Poetics/ as an example. Actually, there is
already a canonical citation pattern using Bekker pages, but we are
interested in using CTS urns. For example,

#+begin_example

#+end_example

=tlg0086.tlg034.perseus-grc2= is a Perseus encoding of an edition of the
/Poetics/; this citation points to "chapter 1, subchapter 1" in an
agreed-upon structure

Here is a portion of the (updated) encoding:

** Decide fate of normalizers.py
:PROPERTIES:
:CUSTOM_ID: decide-normalizers-fate
:ASSIGNEES: Cliff
:SOURCE: chat/2026-05-16
:END:

=mvp/normalizers.py= implements two phases originally designed to
support the annotation pipeline: phase 2 repairs =xml:base= on citable
elements; phase 3 adds =xml:id= derived from those =xml:base= values.
Both were motivated by the old =tei_citation_pipeline= approach.

Now that =ReferenceParser= uses =<citeStructure>= as its primary
mechanism, and =xml:base= / =xml:id= are no longer required inputs to
citation resolution or generation, the normalizers' role is unclear.

*** Research
[2026-05-16] Analyzed in consultation with Claude Chat.

Two options:

1. *Retire the normalizers.* The corpus migration path runs directly
   from =<cRefPattern>= to =<citeStructure>=, bypassing =xml:base= and
   =xml:id= normalization entirely.  A new =cRefPattern=→=citeStructure=
   converter (not yet written) would replace the normalizers in the
   migration pipeline.  The normalizers would be deleted or archived.

2. *Retain the normalizers as a separate concern.* Even if
   =ReferenceParser= doesn't need =xml:id=, other consumers (the XSLT
   chunkers, the SpaCy bridge, external tools) might.  The normalizers
   would remain as optional preprocessing steps, decoupled from the
   citation resolution path.

The =ReferenceAuditor= already reports which documents have =<cRefPattern>=
and their pattern structure — this is the data a future converter would
consume.

*** Decision
:PROPERTIES:
:DISPOSITION: adopt
:END:
[2026-05-19] Retain and rewrite the normalizers, with a narrowed scope.

/Revised [2026-05-23]: see below./

The old phases 2 and 3 (repairing =xml:base= on every citable element,
adding =xml:id= from =xml:base=) are obsolete: =xml:base= on non-=<body>=
elements is no longer part of the encoding convention, and the old
heuristic reconstruction of URNs is superseded by =ReferenceParser=.

The new normalizer's job is narrower and runs *after* migration (i.e.
after =transform1.xsl= or equivalent has produced a conformant document
with =<body @xml:base>= and =<citeStructure>=):

1. Run =ReferenceParser.citations()= over the document.
2. For each citable element, add =@xml:id= derived from the passage
   component of its CTS URN (e.g. =section-17=, =b1-ch2-s3=).
3. Strip any legacy =xml:base= attributes from non-=<body>= elements.

This gives every citable element a stable, URN-derived HTML anchor
before the citation index is generated and before the XSLT runs.
The citation index generator can then read =@xml:id= directly from
the document rather than computing it separately.

**** Revised decision [2026-05-23]: retire the normalizers entirely.

Nothing downstream reads =@xml:id= attributes on TEI elements.
=ReferenceParser= resolves all citable elements from =<citeStructure>=
at build time, so there is no value in pre-stamping attributes on the
source document.  The =CitationIndexGenerator= (=mvp/citation_index.py=) computes the
URN→xml_id mapping itself and writes it to the JSON sidecar; the XSLT chunkers will receive that sidecar as an
=xsl:param= and generate HTML anchors during the transform.

=mvp/normalizers.py= and =src/python/tei_citation_pipeline.py= have been
deleted.  The =tei-audit= CLI entry point has been removed from
=pyproject.toml=.  See branch =retire-normalizers=.


** Design: Citation Index and Chunker Integration
:PROPERTIES:
:CUSTOM_ID: design-citation-index-chunker
:ASSIGNEES: Claude Chat, Cliff
:SOURCE: chat/2026-05-16
:END:

=ReferenceParser= is implemented and tested in isolation.  Nothing in
the build pipeline currently calls it.  The compiled HTML contains no
CTS URNs, no navigation links derived from citation structure, and no
passage anchors.  This item designs the bridge between
=ReferenceParser= and the compilation pipeline.

*** Research
[2026-05-16] Initial analysis by Claude Chat.

The core question is: at what point does a TEI element acquire its CTS
URN in the compilation pipeline, and how does that URN reach the HTML?

The chunkers (=generate_div_chunks.xsl=, =generate_chunks.xsl=) operate
purely on TEI structure.  They know nothing about CTS URNs.  Navigation
links (previous/next) and passage anchors currently use structural
identifiers (=@n=, =@xml:id=), not URNs.

Two candidate architectures:

1. *Citation index (preferred).* Run =ReferenceParser.citations()= over
   each TEI document during the build, write the full citation table to
   a JSON sidecar file (e.g. =tlg0059.tlg002.perseus-grc2.citations.json=),
   and pass that sidecar to the XSLT stylesheets as a parameter or
   secondary input document.  The XSLT reads the index to resolve
   navigation links and emit =<a href>= elements with URN-based targets.
   This is consistent with MVP's static-compilation philosophy: generate
   artifacts once, consume them downstream.

   - [2026-05-19 Tue] Cliff agrees.

3. *Direct Python integration.* Have the Python compilation pipeline
   (=pipeline.py=, =compilers.py=) call =ReferenceParser.generate()= on
   each chunk element and inject the resulting URN into the XSLT
   transformation as a parameter.  More tightly coupled; harder to
   parallelize.

The citation index approach keeps the Python/XSLT boundary clean and
allows the index to be used by other consumers (catalog generation,
passage alignment, external services).

**** Citation index format (strawman)

#+begin_src json
{
  "base_urn": "urn:cts:greekLit:tlg0059.tlg002.perseus-grc2",
  "citations": [
    { "urn": "urn:cts:greekLit:tlg0059.tlg002.perseus-grc2:17",
      "unit": "section",
      "xml_id": "section-17",
      "depth": 0 },
    ...
  ]
}
#+end_src

The =xml_id= field provides the HTML anchor target; the =urn= field
provides the canonical citation; =depth= supports TOC generation.

(*NB*: The TEI documents don't have xml:id attributes (at least not
uniformly). When should those be generated?
*** Decision
[2026-05-19] Adopt the citation index architecture.  Decisions on all
open questions below.

**** Pipeline order

#+begin_example
TEI source
  → migration stylesheet (transform1.xsl or equivalent)
      produces: <body @xml:base>, <citeStructure>, hoisted @type values
  → normalizer (new phase 2)
      produces: @xml:id on every citable element, legacy xml:base stripped
  → citation index generator
      produces: per-document JSON sidecar
  → XSLT chunkers
      consumes: TEI + JSON sidecar → HTML with anchors and nav links
#+end_example

**** Citation index format (revised)

The =xml_id= field is read directly from =@xml:id= on the matched
element (placed there by the normalizer); it is not computed by the
index generator.

#+begin_src json
{
  "base_urn": "urn:cts:greekLit:tlg0059.tlg002.perseus-grc2",
  "citations": [
    {
      "urn": "urn:cts:greekLit:tlg0059.tlg002.perseus-grc2:17",
      "unit": "section",
      "xml_id": "section-17",
      "depth": 0
    }
  ]
}
#+end_src

**** Answers to open questions

- *Per-document or aggregated?* Per-document for the build pipeline:
  one JSON sidecar per TEI file, named
  =<stem>.citations.json=, living alongside the compiled HTML.  An
  aggregated corpus-level index is deferred to the catalog and
  cross-reference work.

- *How does XSLT consume the index?* Via Saxon's =json-doc()= function
  (XSLT 3.0 / Saxon 12).  The stylesheet loads the sidecar with
  =json-doc($citations-path)= and navigates it as a map.  This avoids
  a format-conversion step and is consistent with the project's
  existing use of Saxon.  The sidecar path is passed as an =xsl:param=.

- *Previous/next navigation?* Adjacent URN at the same depth as the
  current chunk.  The chunker already knows the chunk sequence from its
  pre-collected metadata; the citation index provides the URN for each
  position.  The XSLT joins on =xml_id= from the sidecar to construct
  the nav link.

- *Should =SiteMap= own the citation index path?* Yes, by analogy with
  how it owns all other output paths.  A =citations_path(urn)= method
  should be added to =SiteMap=.

**** Definitive pipeline workflow [2026-05-23]

The =@xml:id=-on-element approach has been dropped (see
=#decide-normalizers-fate=).  The =CitationIndexGenerator= computes the
URN→xml_id mapping itself; the XSLT receives it via JSON sidecar.

  prepared TEI
    → CitationIndexGenerator  (mvp/citation_index.py — DONE)
        calls ReferenceParser.citation_records(depth=-1)
        produces: citations.json sidecar  (path via SiteMap.citations_path())
    → PageCompiler / XSLT chunkers
        consumes TEI + JSON sidecar via json-doc($citations-path)  [TODO]

** Design: Milestone-Based Citation and Chunking
:PROPERTIES:
:CUSTOM_ID: design-milestone-citation
:ASSIGNEES: Claude Chat, Cliff
:SOURCE: chat/2026-05-19
:DEPENDS: design-citation-index-chunker
:END:

Many texts in the Perseus corpus use =<milestone>= elements as their
primary citation unit — cards in the Argonautica, Bekker pages in
Aristotle, Stephanus pages in Plato.  The =<citeStructure>= mechanism
and the citation index / chunker integration designed in
=#design-citation-index-chunker= address div-based texts first.  This
item extends that design to milestone-based texts.  It should not be
implemented until the div-based pipeline is working end-to-end.

*** Research
[2026-05-19] Analysis by Claude Chat and Cliff.

**** The structural problem

=<citeStructure>= is designed around containment: each level matches
elements that contain the next level.  Milestones are different in
kind — =<milestone unit="card" n="1"/>= marks a point in a content
stream; the content "belonging to" card 1 is everything between it and
the next =<milestone unit="card">= in document order.  This is a range,
not a subtree, and =<citeStructure>= has no native way to express extent.

For citation /resolution/ this is manageable: =<citeStructure>= can
match the milestone element itself and return it as the citation anchor.
For /chunking/, the extent must be computed by the XSLT — collect
everything from the anchor milestone to the next milestone of the same
unit.  The existing =generate_chunks.xsl= already does this via
=local:before-stop= and =local:after-start=; the design task is to
connect that mechanism to the citation index.

**** Two distinct cases

1. *Milestones as the primary citation unit* (Argonautica cards,
   Bekker pages in Aristotle).  The =<div>= structure in these texts
   is vestigial or purely editorial; milestones /are/ the citation
   hierarchy.  A single-level =<citeStructure>= matching the milestone
   elements directly is the appropriate declaration.

2. *Milestones as a secondary, parallel citation system* (Bekker in
   the Poetics, Stephanus in the Apology).  The primary citation
   hierarchy is div-based; milestones represent an incommensurable
   scholarly tradition.  These require a separate =<refsDecl>= with
   =default="false"= (see =#citation-structures= for the multi-refsDecl
   design).

**** Proposed =<citeStructure>= for case 1

#+begin_src xml
<refsDecl xml:id="cite_by_card" default="true">
  <citeStructure match="/tei:TEI/tei:text/tei:body" use="@xml:base">
    <citeStructure unit="card" delim=":" 
                   match="tei:milestone[@unit='card']" use="@n"/>
  </citeStructure>
</refsDecl>
#+end_src

=ReferenceParser.resolve()= returns the =<milestone>= element.  The
XSLT chunker uses it as a start marker and collects content up to the
next =<milestone unit="card">= in document order.  This is a small but
important semantic extension to =ReferenceParser=: for div-based texts
the returned element /contains/ the cited content; for milestone-based
texts it /anchors/ the cited content stream.  This distinction must be
documented and, if necessary, reflected in the citation index format
(e.g. a boolean =is_anchor= flag, or a =citation_type= field with values
=container= / =anchor=).

**** On =@spanTo=

The TEI provides =@spanTo= (=att.spanning=) as an explicit mechanism for
marking the endpoint of a span beginning at an empty element:

#+begin_src xml
<milestone unit="card" n="1" xml:id="card-1" spanTo="#card-2"/>
<milestone unit="card" n="2" xml:id="card-2" spanTo="#card-3"/>
#+end_src

This makes span extent explicit and robust to edge cases where
document-order traversal would be ambiguous (nested milestone types,
irregular alternation).  However:

- The Perseus corpus does not currently use =@spanTo= on milestones.
- For well-behaved milestone sequences, =following-sibling::milestone
  [@unit='card'][1]= gives the same result without the maintenance
  burden.
- Keeping =@spanTo= consistent across editorial changes to a large
  corpus is non-trivial.

*Decision (provisional):* do not require =@spanTo= for the milestone
citation design.  Use document-order traversal as the default.
=@spanTo= may be used as an explicit override for texts where
milestone structure is ambiguous, but the pipeline should not depend
on it.

**** Relationship to the normalizer

The normalizer (revised in =#decide-normalizers-fate=) must handle
milestone elements in addition to div and leaf elements:
- Add =@xml:id= to every =<milestone>= that is a citable unit
  (i.e. whose =@unit= value appears in a =<citeStructure>=).
- Derived the same way as for other elements: from the passage
  component of the CTS URN returned by =ReferenceParser.generate()=.

*** Open questions

- Does =ReferenceParser= need an explicit =citation_type= property
  (=container= vs =anchor=) on returned elements, or is it sufficient
  to let callers inspect whether the element is empty?
- For texts with both div structure and milestone citations (e.g. a
  prose text chunked by =<div>= but with Bekker milestones inside),
  how does the XSLT decide which chunking strategy to apply?  Is this
  driven by which =<refsDecl>= is =default="true"=, or by a separate
  build configuration?
- Milestone-based texts often have introductory prose in =<div>=
  elements before the first milestone.  How is that content cited and
  chunked?  Does it get a synthetic URN, or is it excluded from
  citation?
- Should =citations()= on a milestone-based document yield URNs in
  document order of the milestone elements, or in numeric order of
  =@n=?  These may differ if milestones are not strictly sequential
  in the source.

The new =select()= should:

1. *Editorial override (fast path)*: check for
   =<refState n='chunk' unit='...'>= in =encodingDesc=.  If present,
   return the matching strategy immediately without running the
   heuristic.  This lets editors declare a preferred chunk level
   explicitly.

2. *Structural heuristic*: collect all distinct =(type, subtype)=
   pairs from =<div>= elements in =tei:text=, skipping the outermost
   edition div (whose =@n= is the CTS URN).  For each candidate,
   compute:
   - instance count
   - mean character length of text content (=text_content= defined
     as the serialized text of the div, excluding descendant div
     text — i.e. only the direct text content, not recursively
     summed)

   Filter candidates:
   - too small: mean char length < 150
   - too large: mean char length > 8000

   Among surviving candidates, prefer the most specific (deepest in
   the hierarchy).  If no candidate survives the filter, fall back to
   the deepest level regardless (don't raise, just pick something).

   The thresholds (150, 8000) are initial educated guesses.  They
   should be defined as named constants at the top of the module so
   they are easy to tune after corpus testing.

3. *Milestone fallback*: if no structural divs with subtypes are
   found, fall through to the existing milestone inspection logic
   (=card=, =section=, =line=, in that order).  Keep a minimal
   =_MILESTONE_FALLBACKS= list for this case.

4. *Hard fallback*: if nothing matches, raise =ValueError= as before.

*Deviations and elaborations from the spec:*

1. *Too-large / too-small fallback split* (Gap 1, not in original spec).
   When all div candidates fail the size filter, the spec said "fall
   back to deepest regardless."  Corpus testing showed this was wrong
   for texts like the Argonautica, which has a single book-level =<div>=
   wrapping the entire text (~70 000 chars).  The implementation now
   distinguishes: too-small candidates fall back to deepest (useful for
   short test fixtures), but too-large candidates yield to milestone
   fallback instead.  Result: Argonautica → =MilestoneStrategy(card)=.

2. *Flat-drama collapse* (Gap 2, not in original spec).  Corpus testing
   with Aristophanes revealed texts where a single =<div type="textpart">=
   carries 20+ distinct one-off subtypes (=Prologue=, =Episode=,
   =Parodos=, =Exodos=, …).  Picking any one subtype as =chunk_unit=
   would make the XSLT produce one page and miss all other sections.
   The fix: when a div type has more than =MAX_SUBTYPES_PER_DIV_TYPE=
   (5) distinct subtypes, all its elements are collapsed into a single
   =(type, None)= candidate, so =chunk_unit= is the type and the XSLT
   chunks at every =<div type="textpart">= regardless of subtype.

3. *Absolute nesting depth*.  The spec said "prefer the most specific
   (deepest in the hierarchy)" without defining "depth."  The initial
   implementation counted matching ancestors in the path, which failed
   for the Politics: =book= and =bekker_page= divs both showed depth 1
   even though =bekker_page= is nested inside =book=.  The final
   implementation counts absolute div-nesting depth from =<tei:text>=,
   giving =book= depth 2 and =bekker_page= depth 3.

4. *Direct-text length excludes div-child tails*.  The initial
   =_direct_text_length= function included the tail whitespace of child
   =<div>= elements (newlines after closing tags), which made the
   Politics =book= divs appear to have 165 chars of "content" when they
   held only whitespace.  The fix: exclude tails of div children.
   Container divs with no prose content of their own now correctly
   read as near-empty (<10 chars) and fall into the too-small pool,
   yielding to their leaf-level children.

5. *Sophocles corpus test updated*.  The old test asserted
   =MilestoneStrategy(card)= for =tlg0011= with a comment "This

** Driver/Chunker Architecture
:PROPERTIES:
:CUSTOM_ID: driver-chunker-architecture
:SOURCE: chat/2026-05-21
:END:

The =driver.xsl= concept was designed but never implemented: the page
shell currently lives inside the chunkers (=generate_div_chunks.xsl=,
=generate_chunks.xsl=), and =driver.xsl= remains a stub.  This was
discovered during PR review of [[#implement-tei-to-html-process]]: the
=morph-url= parameter has no clean home, and =generate-html-from-tei=
documentation points to a chunker rather than a driver as the XSL
entry point.

This needs a design pass before any further implementation:
- What is the driver→chunker interface?
- Where does the page shell live?
- How does =$morph-url= (and future parameters like it) get declared once?

*** Research
[2026-05-22] Claude Chat

**** The problem

The chunkers (=generate_div_chunks.xsl=, =generate_chunks.xsl=) are
currently doing three things: iterating over chunks, computing page
metadata (prev/next, TOC, breadcrumb, doc-lang), and constructing the
full HTML page shell.  The page shell belongs in the driver, not in
the chunkers.  This conflation means:

- The page layout cannot be changed without modifying the chunkers.
- Parameters that are rendering concerns (=$morph-url=, future
  =$citation-map=) must be declared in every chunker separately.
- =driver.xsl= is a useless stub.

**** The division of responsibility

- *Chunker* :: a pure iterator.  Knows how to traverse a TEI document
  and identify chunk boundaries.  Computes lightweight metadata for
  each chunk (position, prev/next filenames, TOC entries, doc-lang,
  work-title, author).  Calls a named template =page:render= defined
  by the driver, passing the raw TEI chunk element and metadata.
  Never touches =<html>=, =<head>=, =<body>=, or CSS.  Never knows
  about =$morph-url= or any other rendering enrichment.

- *Driver* :: the composition root and page assembler.  Imports the
  rendering library and the chunker.  Declares all enrichment
  parameters (=$morph-url=, =$citation-table=, etc.) as top-level
  stylesheet parameters.  Defines =page:render= and supporting named
  templates (=page:header=, =page:footer=, =page:sidebar-left=,
  =page:sidebar-right=, =page:passage-header=).  Loads enrichment
  data (e.g. =document($citation-table)=).  *Triggers rendering*
  inside =page:render= by calling =<xsl:apply-templates mode="chunk">=
  on the chunk element's children, injecting all enrichments as tunnel
  parameters at that point.

- *Rendering library* (=perseus_base.xsl= and descendants) :: declares
  enrichment tunnel parameters (=$morph-url=, =$citation-map=) only in
  the templates that consume them.  Degrades gracefully when parameters
  are absent (empty string / empty sequence defaults).  Has no
  knowledge of where enrichments came from.

**** Why the driver triggers rendering

The driver must call =apply-templates= on the chunk content, not the
chunker.  This is because the driver is the only participant that knows
which enrichments are active for this compilation run.  If the chunker
pre-rendered content and handed it to the driver as a result tree
fragment, the enrichment tunnel parameters would have to be declared
in the chunker — which reintroduces the coupling we are trying to
eliminate.

**** Enrichment parameters

Two enrichment parameters are currently in scope:

- =$morph-url= (=xs:string=, default =''=) :: when non-empty, each
  word token in =text()= is wrapped in an =<a>= linking to the
  morphological server.  Consumed by the =text()= template in
  =perseus_base.xsl=.  This is an interim mechanism pending
  compiled-links-via-=document()=.

- =$citation-table= (=xs:string=, default =''=) :: path or URL of a
  compiled citation link table (XML or JSON).  When non-empty, the
  driver loads it via =document($citation-table)= into a
  =$citation-map= variable and injects it as a tunnel parameter.
  Consumed by the =tei:bibl= rendering template in =perseus_base.xsl=,
  which turns =<bibl n="some-citation">= into =<a href="...">= when a
  matching entry is found, and falls back to a plain =<span>= when not.
  *Note*: the citation link table format and the =tei:bibl= rendering
  template are not yet designed; this parameter is declared now so the
  driver interface is stable.

**** The named-template interface

The chunker calls one template that the driver must define:

#+begin_src xml
<xsl:call-template name="page:render">
  <xsl:with-param name="chunk"       select="."/>   <!-- tei:div or equiv -->
  <xsl:with-param name="work-title"  select="$work-title"/>
  <xsl:with-param name="author"      select="$author"/>
  <xsl:with-param name="doc-lang"    select="$doc-lang"/>
  <xsl:with-param name="chunk-label" select="..."/>
  <xsl:with-param name="file-name"   select="$file-name"/>
  <xsl:with-param name="prev-file"   select="$prev-file"/>
  <xsl:with-param name="next-file"   select="$next-file"/>
  <xsl:with-param name="all-chunks"  select="$all-chunks"/>
</xsl:call-template>
#+end_src

The driver's =page:render= implementation applies rendering to the
chunk content:

#+begin_src xml
<xsl:template name="page:render">
  <xsl:param name="chunk"      as="element()"/>
  <xsl:param name="work-title" as="xs:string"/>
  ... (other metadata params)

  <xsl:variable name="citation-map"
    select="if ($citation-table != '')
            then document($citation-table) else ()"/>
  <html>
    ...
    <div class="text-body">
      <xsl:apply-templates select="$chunk/node()" mode="chunk">
        <xsl:with-param name="morph-url"    tunnel="yes" select="$morph-url"/>
        <xsl:with-param name="citation-map" tunnel="yes" select="$citation-map"/>
      </xsl:apply-templates>
    </div>
    ...
  </html>
</xsl:template>
#+end_src

The =page:= prefix is a naming convention only (XSLT named templates
do not use XML namespaces); it signals that these templates form the
driver's public interface.

**** Resolution of the morph-url boundary issue

This design also resolves the boundary violation noted in the review
of [[#implement-tei-to-html-process]]: =$morph-url= was previously
tunneled from =mode="chunk"= into =mode="tei-to-html"=, technically
crossing the mode boundary.  In the new design it is injected by the
driver at the =apply-templates= call, so it enters =mode="chunk"= from
outside the chunking infrastructure entirely.  The rendering library
simply declares it as a tunnel parameter; the driver is responsible
for supplying it.

*** Decision
[2026-05-22]
Adopt the design above.  See [[#implement-driver-chunker-architecture]]
for the implementation task.

***** Document encoding requirements
:PROPERTIES:
:CUSTOM_ID: document-encoding-requirements
:END:

=ReferenceParser= requires the following encoding conventions, which
differ from the current Perseus corpus defaults and must be enforced by
the =StructureAuditor=:

1. The CTS base URN must appear in =@xml:base= on =<body>=, not on
   =<div type="edition">=:
   #+begin_src xml
   <body xml:base="urn:cts:greekLit:tlg0086.tlg034.perseus-grc2">
   #+end_src

2. The root =<citeStructure>= must use =use="@xml:base"= to pick up that value:
   #+begin_src xml
   <citeStructure match="/tei:TEI/tei:text/tei:body" use="@xml:base">
     <citeStructure unit="chapter" delim=":" match="tei:div" use="@n">
       <citeStructure unit="subchapter" delim="." match="tei:p" use="@n"/>
     </citeStructure>
   </citeStructure>
   #+end_src

3. The =<refsDecl>= containing the canonical CTS =<citeStructure>= must
   carry =default="true"=.  A document may have multiple =<refsDecl>=
   elements representing incommensurable citation systems (e.g. CTS
   chapter/subchapter and Bekker page/column/line); =default="true"=
   identifies the primary one.

***** Class interface

#+begin_src python
class ConfigurationError(Exception):
    """Raised when no usable citeStructure can be found or selected."""

class CitationError(Exception):
    """Raised when a URN is syntactically invalid or resolves to nothing."""

class ReferenceParser:
    def __init__(
        self,
        tei_doc: TEIDocument,
        refsDecl_id: str | None = None,
    ) -> None: ...

    def resolve(self, urn: str) -> etree._Element:
        """Return the element identified by the full CTS URN.

        Partial citations (e.g. book only, when book/chapter/section is
        the full hierarchy) are valid and resolve to the element at that
        level.  Raises CitationError if the URN is malformed or matches
        nothing.
        """

    def generate(self, element: etree._Element) -> str:
        """Return the full CTS URN for a citable element.

        Raises CitationError if the element is not reachable from any
        level of the active citeStructure.
        """

    def citations(self, depth: int = -1) -> Iterator[str]:
        """Yield every resolvable CTS URN in document order.

        depth=-1 (default): yield citations at every level of the
            hierarchy (suitable for TOC generation).
        depth=0: yield only root-level citations.
        depth=N (positive): yield citations up to and including level N
            (0-based), suitable for feeding the chunkers with leaf-level
            citations only.
        """
#+end_src

***** Resolution algorithm

Given a full CTS URN such as
=urn:cts:greekLit:tlg0086.tlg034.perseus-grc2:1.3=:

1. Split on the first =:= that follows the version identifier to
   separate the base URN from the passage component.  The base URN is
   everything up to and including the version token
   (=urn:cts:greekLit:tlg0086.tlg034.perseus-grc2=); the passage
   component is everything after the separating =:= (=1.3=).

2. Verify the base URN matches =body/@xml:base=.  Raise =CitationError= if not.

3. Walk the =<citeStructure>= tree level by level.  At each level:
   a. Take the next passage token (splitting on the =@delim= declared
      at that level).
   b. Evaluate the level's =@match= XPath relative to the element
      matched at the previous level (or relative to the document root
      for the root =<citeStructure>=).
   c. Among the matched elements, find the one whose =@use= value
      equals the current token.
   d. If no element matches, raise =CitationError=.

4. Stop when passage tokens are exhausted.  The element matched at the
   last consumed level is the result.  Partial citations are valid:
   =urn:…:1= resolves to the chapter div, =urn:…:1.3= to the paragraph.

5. Multiple =<citeStructure>= children at the same level (the Ovid
   case — structural irregularity within a work): try each sibling in
   document order and take the first whose =@match= XPath yields a
   result for the current token.  If none match, raise =CitationError=.

***** Generation algorithm

Given an =etree._Element=:

1. Walk the =<citeStructure>= tree to find the level whose =@match=
   XPath, evaluated from the appropriate ancestor, yields this element.
2. Collect =@use= values walking from the root level down to the matched
   level, assembling the passage component by joining with =@delim=
   values.
3. Prepend the base URN (from =body/@xml:base=) with a =:= separator.
4. Raise =CitationError= if the element is not reachable from any level.

***** =citations()= implementation

Recursive walk of the =<citeStructure>= tree.  At each level, evaluate
the =@match= XPath relative to each element matched at the parent level,
and yield a URN for every match.  Recurse into children unless the
current depth equals the =depth= parameter.  Yield in document order.

***** Straddling-boundary case (critical invariant)

=<xsl:apply-templates mode="chunk"/>= on their children, /not/
=mode="tei-to-html"=.  This is required to preserve correctness when a
container element (e.g. =tei:div=, =tei:p=) straddles a milestone

on the far side of the boundary would be emitted when it should be
suppressed.  The exception is =tei:body=, which recurses in
=mode="tei-to-html"= because there is no chunking context at the body
level.  Leaf elements (=tei:gap=, =tei:lb=, =tei:pb=, =tei:milestone=,
=text()=) do not recurse and so have no mode-choice to make.

***** =tei:l= and =@xml:base=

The previous implementation of =tei:l= relied on a =$base-urn= tunnel
parameter passed down from the chunker.  This was replaced: the
template now reads =ancestor::tei:body/@xml:base= directly.  If the
attribute is absent, the transformation terminates with an error
message.

Consequence: every TEI document that contains =tei:l= elements must
have =xml:base= set on its =<body>= element.  The value should be the
CTS URN for the edition (e.g.
=urn:cts:greekLit:tlg0001.tlg001.perseus-grc2=).  All test fixtures
under =tests/data/= were updated accordingly.  Note that =tests/data/=
is gitignored; force-add with =git add -f= is required to stage those
files.

The =$base-urn= local variable still exists in the chunkers (used by
=local:chunk-cts-range()= and the CTS range chip in the passage
header); it is simply no longer tunneled into =mode="chunk"=.

***** New templates (output changes from baseline)

Two element types that previously fell through the catch-all (emitting
content but no wrapper element) now have dedicated templates:

- =tei:lg= → =<div class="lg">= (recurses in =mode="chunk"=)
- =tei:stage= → =<div class="stage">= (recurses in =mode="chunk"=)

Documents containing these elements will have additional wrapper
=<div>= elements in the output compared with a pre-refactoring
baseline.

=local:strip-punct= was moved from =chunker_core.xsl= to
=tei/perseus_base.xsl=, where it is used exclusively (by the =text()=
rendering template).

***** =generate-html-from-tei= CLI

A Python CLI script, =src/python/generate_html_from_tei.py=, was
written as part of this work item.  It takes a TEI file, an XSL driver
file, and an output directory, and runs the transformation via
=saxonche=.  Registered in =pyproject.toml= as the =generate-html-from-tei=
entry point.  The key detail is that =set_base_output_uri= must be
called with the output directory URI before invoking the transformer,
or =xsl:result-document= outputs are written to the wrong location.

**** Non-obvious details

The =page:= and =chunker:= prefixes on named template names are XSLT
QNames and require proper XML namespace declarations in every stylesheet
that uses them.  Both prefixes must be declared in the root
=<xsl:stylesheet>= element and added to =exclude-result-prefixes=.

The =$morph-url= tunnel parameter flow was verified empirically: the
value set in =page:render= flows through the =mode="chunk"= catch-all
(which does not declare it) and arrives correctly at the =text()=
template in =mode="tei-to-html"=, consistent with the XSLT 3.0 spec's
guarantee that undeclared tunnel parameters pass through implicitly.
